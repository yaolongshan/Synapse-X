# OxStream 采集读回顺序

用户已确认：只调整 OxStream 的采集顺序，保留 Host 原路径，随后由用户对照旧版与新版；本次不自动编译、运行、测试、提交或推送。

## 目标与选择

- 原顺序：`Copy → Flush → ReleaseFrame → Map → Pack → Unmap`。
- 采用顺序：`Copy → Map → Pack → Unmap → ReleaseFrame`，Map 仍使用 READ、flags=0。
- 不采用仅删除 Flush 而保留提前释放的做法；新顺序在读取完成前持有桌面帧。
- 跨调用持有桌面帧、延至下一次 Acquire 前释放的方案涉及停止与重建状态，本次不采用。

## 实现范围

- `CaptureFrame` 增加明确的读回顺序枚举参数，默认原顺序；OxStream 显式选择新顺序，Host 和截图工具原调用不变。
- 每次成功 Acquire 后用局部作用域管理帧和映射；失败返回、异常和正常结束均配对释放，已提前释放的帧不再释放。
- 保持 ROI、RowPitch、BGR 打包、LZ4、缓存重发、调度、错误返回和既有阶段统计口径。
- 会话开始日志追加 `capture_readback=map_then_release`，用于识别新版，不增加逐帧日志或细分计时。
- Android 不修改，Wi-Fi 低延迟默认关闭；保留发送端无关运行配置。

## 验收

- 补充纯 C++17 清理用例源码：映射前退出、映射失败、映射后异常、正常清理、提前释放、连续两帧；不执行。
- 静态核对默认参数、调用点、所有释放分支和差异。
- 用户保留旧 Release EXE，固定 640×640、FPS、循环画面和安卓配置，按旧版 → 新版 → 旧版各预热 10 秒、记录 60 秒。
- 对照 PC `capture_ms` 的平均/最大值、采集 FPS 和失败情况，并人工检查颜色、方向、连续启停、显示模式切换。真实 DXGI/驱动行为需要用户实测。
- 不预设收益；安卓首包之后的计时不覆盖这次调整的发生阶段。
